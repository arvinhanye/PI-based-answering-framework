## 3. 主要问题（按严重度排序）

### 3.1 预算硬控制投入过大，且会浪费额度

- **额度很可能用不完。** 粗算：一轮快刷讲解约 4K 输入、300 输出 token，按 §9.3 的价格约 0.01 元；10 元够上千轮。为一个基本不会触顶的上限建 T04 全套（unknown 状态、跨月归属、时钟回拨、多进程抢最后一笔余额），投入产出比很低。
- **服务商余额可以当硬上限。** 据审查人了解，DeepSeek API 是先充值后使用（**未核实，请确认**）。如果属实，每月只充 10 元就是服务端兜底；本地只需要软记账加 80% 提醒。缺点是同一账户的其他用途共享余额，这一点需要在文档里写明。
- **“完整上下文保守预留”会锁死余额。** 模型上下文很大时，单次预留可能是几毛甚至几元，月底余额远大于实际单次费用，请求却已经被拒绝。如果仍然要求可证明的硬上界，建议改用**序列化后最终请求的 UTF-8 字节数**作为输入 token 上界：字节级 BPE 每个字节最多产生一个 token，再加上每条消息固定的模板开销即可。这个界可证明，而且紧得多。需要先确认目标模型的分词器是字节级 BPE。
- **SDK 隐藏重试可以从根上避免。** 受控 provider 的流式实现直接自己写 `fetch`，不经过 SDK，T01 的 `hidden_sdk_retry_is_disabled_or_admitted` 就自然成立。

请修订：
- 【待用户决定】§9 与 T04：在“服务商预付余额作硬上限 + 本地软记账”和“保留本地硬准入”之间二选一。选前者时，删去 T04 中 unknown、跨月、时钟回拨、并发最后余额等用例，只保留记账、提醒、可信改额。
- 若保留硬准入：§9.2 用字节上界替代“完整上下文硬上限”，在 T04 增加对应的定价测试。
- §3 与 T01：明确受控 provider 自行实现 HTTP 发送，不依赖 SDK 的重试逻辑。

### 3.2 为原材料中不存在或很少出现的情形建了大系统

- **简答**：原件中没有简答题，T10（规则版本、临时规则、申诉、重评）却是完整子系统。
- **资料升级与进度迁移**：T07 的三类迁移和选项重映射，面对的是三份静态文件，首版遇到的概率很低。
- **SSRF / DNS rebinding 防护**：如果 Fetch 使用 DeepSeek 的付费 Fetch 服务，抓取发生在服务端，本地 SSRF 防护没有作用对象。§8 末段和 T11 的 `redirect_to_private_ip_is_blocked`、`dns_rebinding_is_blocked` 与“Search、Fetch 走服务商付费接口”存在矛盾。

请修订：
- §8 与 T11：明确抓取发生在本地还是服务端。服务端抓取时删去本地网络防护用例，改为“网页内容视为数据、不得改变预算或规则”的提示注入测试。
- 【待用户决定】首版是否移出 T07、T10，只保留契约占位（题目稳定 ID 和内容哈希照常保存，便于以后迁移）。

### 3.3 通用导入器不如“一次性转换 + 标准 JSON”

三份资料格式各不相同：一份是规则的段落，一份编号不齐且带嵌图，一份是 235 页图片 PDF。建议每份资料写一个专用转换脚本，产出标准 JSON 和人工校对报告；应用本身只读取标准 JSON。“可更换题库”由 JSON schema 保证，这比带模板、checkpoint、暂停续跑和模型辅助整理的通用导入器简单一个数量级。

请修订：
- §5.1 与 T05、T06：把导入拆成“各来源的转换脚本（位于 `pi-study/converters/`）→ 标准 JSON → 应用导入 JSON”。作业暂停、续跑和模型辅助整理推迟到出现第四种来源时再做。
- T05：把“同段多选项拆分”列为首要测试，覆盖选项文本本身含 `B.` 等字样、命令中含大写字母加点号的情形，并对 1508 题全量输出“选项数异常”清单。
- §5.1：记录来源考点标签的实际覆盖率（212/1508），说明其余题目的标签来源。

### 3.4 计划结构问题

- **T03 一次冻结全部契约**，包括 T10、T11 尚未实现的部分，属于预先大设计，后续大概率返工。建议契约随每个纵向切片逐步确定，T03 只锁定首个闭环所需的部分。
- **T01 是探针调研，却套用“先写失败测试”的 TDD 流程。** P0 应该是限时调研，交付一份结论报告；TDD 从 T03 开始。
- **T02 标注为与 T01 可并行，实际依赖 T01 的测试骨架。** 请把骨架单独拆成 T00，或者删去“可并行”的说法。
- **复习间隔不考虑考试日期。** 固定的 1/3/7/14/30 天间隔，在离比赛只剩三周时，等于让一道题不再出现。建议增加可选的 `examDate`：间隔不超过剩余天数，临近考试时提高到期题和错题的比重。
- **多进程共用 SQLite 的细节没有写。** Pi 和 CLI 共用 `node:sqlite` 时，需要明确 WAL 模式、`busy_timeout`，以及写事务使用 `BEGIN IMMEDIATE`，并在 T03 里加多进程写入测试。
- **没有工期估算。** 请给出每个里程碑的预计工作量，并标出用户第一次能刷题、第一次能用 AI 讲解的时间点。

### 3.5 可信提交做得过重

单人本地使用，不需要“不可反序列化的 opaque 一次性凭据，绑定题目版本和答案”。只要两条就能达到同样效果：

1. 不把任何提交、跳过、揭晓类工具暴露给模型；
2. 提交只能来自 Pi 的用户输入拦截、slash 命令、快捷键或 CLI。

P0 真正需要验证的，是 Pi 0.87.1 是否提供可靠的、发生在模型之前的用户输入事件，以及该事件能否把“提交 B”拦下来而不交给模型。

请修订：§6、§10.2 与 T03、T08 中的凭据机制简化为“写入口不注册为工具 + 只在输入事件、命令和 CLI 中调用”，保留幂等键防重复计分。

## 4. 应保留的设计

- 出题视图不带答案和解析；只有明确提交才计分；辅助作答单独标记。
- 原答案原样保留，疑点单独标记（第 3 题解析矛盾、423/586/1065 等缺图题隔离）。
- “参考成绩”和 `unscorable`，不制造虚假的薄弱点。
- 用固定金标准样本验收导入质量，不允许靠全部隔离来凑零错误。
- 查证结果绑定原题，不静默改分。
- 统计口径表（当前表现与历史走势分开、辅助作答另列）。
